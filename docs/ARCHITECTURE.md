# Архитектура Stultus

## Зачем именно так

Три решения, из которых следует всё остальное.

**1. Нейросеть — на общей виртуалке, не на рабочих машинах.** Подписки и
ключи одни на бюро, лежат в `.env` на сервере. Плагин знает только адрес и
пропуск. Заменить модель, поднять лимит, сменить провайдера — правка на
сервере, без переустановки у сотрудников.

**2. Соединение исходящее, из окна плагина.** Плагин не слушает портов.
Поэтому нет конфликта «кто занял 8080» при пяти открытых окнах SketchUp
(на Windows каждое окно — отдельный процесс со своим Ruby), нет правил
брандмауэра на рабочих местах, а окно работает из любой сети, откуда виден
gateway. Сеть живёт в JS окна (`UI::HtmlDialog`), потому что Ruby в SketchUp
однопоточный: ожидание ответа модели из Ruby подвесило бы приложение.

**3. Плагин — это MCP-сервер для модели, а не «ещё один клиент».** Claude
Code и Codex оба умеют MCP. Gateway не переводит вызовы на язык каждого
провайдера, а выставляет одни и те же пять инструментов как MCP-сервер
`stultus` и подключает его к тому процессу, что крутит ход. Добавить третьего
провайдера — написать один файл в `server/src/providers/`.

## Слои

```

│ SketchUp 2024                                                  │
│  ├── Ruby: runner / scene / screenshot / history / settings    │
│  │        ▲ sketchup.callback(id, json)   │ execute_script     │
│  └── HtmlDialog (CEF): app.js — чат, WS-клиент, карточки       │
└─────────────────────────────┬──────────────────────────────────┘
                              │ ws://gateway:8790/ws  (исходящее)
┌─────────────────────────────▼──────────────────────────────────┐
│ gateway (Node 22, Docker, network_mode: host)                  │
│  index.ts      http + ws, реестр окон                          │
│  connection.ts одно окно: очередь tool_call → tool_result      │
│  mcp.ts        MCP-сервер stultus (Streamable HTTP, stateless) │
│  chat.ts       ход: выбрать провайдера, переслать поток        │
│  providers/    claude.ts (Agent SDK), codex.ts (codex-sdk)     │
│                        │ http://127.0.0.1:8790/mcp/<id>        │
│                        ▼                                       │
│  процесс Claude Code / codex exec (сессии в томах)             │
└────────────────────────────────────────────────────────────────┘
```

## Ход, по шагам

1. Пользователь жмёт «Отправить». JS просит у Ruby `scene_state`, кладёт
   снимок сцены к тексту и шлёт `chat` в gateway.
2. `chat.ts` берёт провайдера, подставляет `resume`/`thread_id` из файла
   модели (плагин прислал их в `hello`), запускает генератор.
3. Провайдер стартует процесс модели с MCP-сервером этого окна. Модель
   зовёт `execute_ruby` → MCP-обработчик в gateway шлёт `tool_call` в окно →
   JS зовёт Ruby → Ruby исполняет в одной операции → ответ уезжает обратно
   как `tool_result` → MCP отвечает модели.
4. Текст ответа стримится в окно (`text`), карточки инструментов JS рисует
   сам в момент `tool_call`.
5. `done` с расходом. JS сохраняет переписку в модель (`save_history`) и
   идентификатор сессии (`save_sessions`).

Снимок вьюпорта — тот же путь, только между `tool_call` и Ruby стоит
пользователь: карточка с кнопками. Отказ — обычный `tool_result` с
`ok: false`, модель продолжает.

## Границы и страховки

- **Произвольный Ruby исполняется на рабочей машине.** Это осознанно: без
  него моделирование не работает. Защита — не песочница, а Undo (каждый вызов
  — операция) и то, что gateway пускает только по пропуску, а MCP-эндпоинт
  слушает localhost с уникальным bearer на соединение.
- **Таймаут инструмента** (10 мин) на стороне gateway: если окно закрылось
  посреди хода, модель получает отказ, а не висит.
- **Один ход на окно.** Второе сообщение во время хода отклоняется.
- **Потолок кругов** (`MAX_TURNS`) — страховка от зацикливания, не бюджет.
- **Лимит переписки в модели** — 150 КБ, чтобы `.skp` не рос.

## Что намеренно не сделано в 0.1

- Семантические инструменты (box/pushpull/материал) — только `execute_ruby`.
  Добавлять по мере того, как модель будет ошибаться в одном и том же.
- Автоснимок после построения — снимок только по согласию.
- Учёт расхода по сотрудникам, авторизация по пользователям — один общий
  пропуск.
- Вложения (картинки-референсы) в сообщении пользователя.
